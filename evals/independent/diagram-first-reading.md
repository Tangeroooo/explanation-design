# 그림만으로 읽은 첫 해석

평가 대상은 `../../examples/code/figures/delivery-flow.png`이며, 원본과 의도한 표시 크기인 1280×721 px에서 보았다. 이미지 외 파일·명세·코드는 읽지 않았다. 이 기록은 사실 검증이나 최종 통과 판정이 아니다.

## 핵심 해석

그림은 `deliver(message, sink, broker)`가 `await sink.send(message)`를 먼저 실행하고, 이 호출이 정상 반환한 경우에만 `await broker.ack(message.id)`로 진행하는 순서를 보여준다. 두 호출이 모두 정상 반환하면 `return "acked"`로 끝난다.

독자 질문인 “deliver가 실패했을 때 어디까지 실행되었는가?”의 답은 실패 위치에 따라 두 갈래다.

- `sink.send`에서 예외가 발생했다면: send 호출까지 실행했고 예외가 전파된다. `broker.ack`는 호출하지 않았다. send가 외부에 어떤 효과를 남겼는지는 `send effect: UNKNOWN`으로 표시되어 있어 알 수 없다.
- `broker.ack`에서 예외가 발생했다면: send는 이미 정상 반환했고 ack 호출까지 실행했다. 예외가 전파되며 `return "acked"`에는 도달하지 않는다. `durability / broker state: UNKNOWN`으로 표시되어 있어 영속성과 broker의 실제 상태는 알 수 없다.

따라서 그림만으로는 “deliver 실패 = 전송되지 않음” 또는 “ack 실패 = broker에 반영되지 않음”이라고 결론 내릴 수 없다.

## 호출 순서·경계·소유권

- 중앙의 위→아래 화살표가 정상 진행 순서이며, 두 `RETURNS` 표시가 다음 단계로 진행하는 조건을 나타낸다. 병렬 실행 경로는 그려져 있지 않다.
- 각 await 상자에서 옆으로 나가는 `RAISES` 화살표가 실패 경로다. 왼쪽은 send 실패, 오른쪽은 ack 실패에 연결된다.
- `worker.py:21`, `worker.py:22`라는 위치 표시는 보인다. 해당 코드가 실제로 어떤지는 이미지로 검증할 수 없다.
- 명시적인 시스템 경계나 소유권 구획은 없다. `sink`와 `broker`가 서로 다른 호출 대상이라는 것은 읽히지만, 프로세스·서비스·저장소 경계와 메시지 소유권 이전 시점은 읽히지 않는다.
- 예외를 넘겨받는 호출자는 표시되어 있지 않다. 재시도·복구·외부 상태 변화 역시 그림에는 제시되지 않는다.

## 모호하거나 읽기 어려운 위치

- 주 호출과 예외 설명은 식별 가능하다. 다만 `RAISES`·`RETURNS`, 코드 위치, `UNKNOWN` 설명, 하단 주석은 본문보다 상당히 작아 1280×721 px 표시에서도 주의해서 읽어야 한다. 정확한 폰트는 판별하지 않았다.
- 오른쪽 실패 상자의 “send는 반환함”은 실행 순서를 전달한다. 그러나 바로 아래 `durability / broker state`에서 durability가 무엇의 영속성을 말하는지는 특정되어 있지 않다.
- `return "acked"`는 함수의 반환값으로 읽힌다. 이 문자열이 외부 시스템의 확정 상태를 보증하는지는 그림에 나오지 않는다.
- 오른쪽 실패 상자만 주황색으로 강조되어 있다. 이 차이가 특별한 위험도나 우선순위를 뜻하는지는 범례가 없어 알 수 없다.
- 하단의 “Solid arrows: call / return order in current code”는 화살표가 실행 순서를 나타낸다고 설명한다. `C1–C4 · source S1`은 보이지만, 그 식별자가 어떤 근거와 연결되는지는 이미지 안에 설명되어 있지 않다. “external contracts not supplied”라는 한계도 명시되어 있다.

코드·외부 계약과의 일치 여부는 확인하지 않았다. 외부 부작용이나 영속성은 그림이 명시한 UNKNOWN 범위를 넘어 판단하면 안 된다.
