# 컴포넌트 명세

구조·설계 그림이 컴포넌트·인터페이스·소유권·공유 자원을 설명해야 할 때 [그림 명세](figure-brief.ko.md)와 함께 사용한다. 순서·상태·수치 비교만이 질문이면 생략한다. 의미를 전달하는 명세이며 픽셀 배치도나 모든 구현 세부를 기록하는 양식이 아니다. 공통 명세의 ID와 근거를 참조하고 중복 작성하지 않는다.

## 범위와 계층

- 관점(논리 모듈 / 실행 인스턴스 / 프로세스 / 호스트)과 답할 질문:
- 해당 시 상위 그림과의 대응; 내부 분해와 배포·다른 관점으로의 전환을 구분:
- 경계 종류·소유자·인스턴스 수가 있는 포함 관계 트리; 범위나 미확인 수량은 명시:
- 펼칠 부분 / 요약할 부분 / 상세 그림으로 옮길 부분과 독자 질문에 따른 이유:

## 컴포넌트

의미 있는 컴포넌트나 반복 그룹마다 항목 하나를 기록하고, 유형과 그 인스턴스를 구분한다. 표 또는 짧은 레코드를 사용한다. 독자 질문에 관련된 필드만 채우되, 해석에 영향을 주는 공백은 **미상**, **해당 없음**, **생략과 그 이유**로 구분한다. 근거에 없는 인터페이스나 내부 모듈을 만들지 않는다.

- 고정 ID / 정확한 표시 이름 / 종류 / 출처와 사실·추론·제안·미확인 구분:
- 상위 경계 또는 소유자 / 수량과 인스턴스 범위 / 해당 시 공유 사용자:
- 책임 / 보여줄 내부 요소나 상태 / 근거가 있는 인터페이스 또는 접근 지점:
- 표현: 도형과 그 의미 / 포함 경계·내부 구획·접점·반복 단위 / 상세 또는 요약 / 반드시 남길 구분:

공유 자원은 실제 소유 범위 안에 한 번 기록한다. 반복 그룹을 요약해도 수량과 인스턴스별 상태 귀속은 보존한다. 공통 소스 정의가 실행 인스턴스 하나를 뜻하지는 않는다. 소유자가 미상인 대상을 경계 안에 넣어 소유권을 암시하지 않는다. 명시되지 않은 API에 장식용 접점을 만들지 않는다.

## 관계

중요한 관계마다 다음을 기록한다.

- 출발 ID와 관련 접점 → 도착 ID와 관련 접점(또는 무방향 쌍); 접점이 미상이거나 무관하면 컴포넌트를 끝점으로 사용:
- 의미: 소속·의존·호출·읽기/쓰기·전달·자원 사용 등 / 방향과 라벨 / 출처와 주장 구분:
- 전달 내용·순서·동기화·조건·실패 계약은 **질문과 관련 있고 근거가 있을 때만** 기록; 해석에 영향을 주는 미상은 명시:
- 표현: 포함 또는 선 / 끝점과 화살표의 의미; 실행 순서를 주장하는지 구분:

소속은 계층으로 표현하면 별도 edge 목록에 중복 기록하지 않아도 된다. 참조 ID는 실제 명세 항목과 대응해야 한다. 연결이 빠진 이유를 미상 또는 의도적 생략으로 기록하고 그럴듯한 경로를 그려 넣지 않는다.

## 제작 전 점검

제작자가 새로운 시스템 사실을 결정하지 않고도 관련 경계·수량·공유·내부 상세·관계 의미를 정할 수 있는가? 인스턴스 하나와 중요한 연결 하나를 출처에 대조한다. 알고 있지만 빠뜨린 사실은 명세에 보완한다. 모르는 사실은 미상으로 남기고 답에 영향을 주는 한계를 그림에서도 드러낸다. 일상적인 사용자 승인 단계로 만들지 않는다.

복잡하면 개요와 상세를 대응시키거나 반복 그룹을 요약하되 소유권과 수량을 보존한다. 노드 수 제한을 맞추려고 필요한 구조를 단계 나열로 평탄화하거나 핵심 구분을 삭제하지 않는다. 좌표·간격·선 경로는 diagram-design에서 결정한다.
