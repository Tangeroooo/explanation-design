# 표현 선택

| 전달할 관계 | 우선 표현 | 그림으로 전환할 조건 |
|---|---|---|
| 단일 사실·조건 | 짧은 문장 | 보통 불필요 |
| 정확한 속성·대안 | 표 | topology 변화가 선택을 좌우함 |
| 실제 분기·API 사용 | 짧은 코드 | 여러 actor·상태·실패가 얽힘 |
| 책임·경계·연결 | architecture | 연결과 경계 자체가 질문 |
| 호출의 시간 순서 | sequence | 응답과 부수 효과 순서가 중요 |
| guard·상태 변화 | state / flowchart | 예외 분기를 따라가야 함 |
| 수치 차이·분포 | 표 또는 plotting chart | 규모·추세·분포가 표보다 분명함 |

그림마다 하나의 질문과 한 문장 메시지를 먼저 정한다. 명세는 [figure-brief](../assets/figure-brief.ko.md)를 사용한다. source·claim ID와 관계를 연결한다. node만 아니라 **edge에도** 근거를 남긴다. 화살표는 의존·호출·데이터·시간 중 무엇인지 라벨 또는 범례로 정한다.

- 서로 다른 보장을 가진 단계는 “처리 완료” 하나로 합치지 않는다.
- 색은 구분을 돕되 사실/제안·성공/실패를 색에만 의존하지 않는다.
- node가 많아 질문을 잃으면 overview + detail로 분리하고 연결 기준을 명시한다.
- 생략한 것 중 해석을 바꿀 수 있는 항목은 캡션·본문에 쓴다. 재시도나 외부 저장소를 생략하고 무손실을 암시하지 않는다.
- 정확한 데이터 차트는 [data](data.ko.md)를 따른다. 장식용 면적·아이콘 크기로 수치를 암시하지 않는다.

그림을 지웠을 때 잃는 이해가 없다면 만들지 않는다. 그림을 봐도 근거가 늘지는 않는다. 의미 검증은 제작 이후에도 explanation-design의 책임이다.

## 관계에서 형태를 고른다

도구나 템플릿보다 독자가 보아야 할 관계를 먼저 정한다. 사각형은 경계와 상태를 표현하는 데 유용하다. 문제는 관계를 표현하지 않은 채 문장에 테두리만 두르는 것이다.

| 질문 | 유용한 형태 | 반드시 드러낼 것 |
|---|---|---|
| 무엇이 무엇을 소유하거나 포함하나? | 중첩 경계, 반복 인스턴스 | 범위·소유권, 공유 자원과 인스턴스별 자원 |
| 같은 공간을 어떻게 다르게 나누나? | 공통 축 위에 정렬한 구간 띠 | 서로 다른 경계·겹침·대응 관계. 없는 포함 관계를 만들지 않음 |
| 객체 하나가 어디로 가고 어떻게 바뀌나? | 같은 객체를 장소별 또는 전후로 추적 | 식별자와 물리 위치, 복사본·버전·공개 시점의 구분 |
| 누가 실행하고 기다리며 동시에 동작하나? | sequence 또는 actor별 lane, 대기·gate | actor·메시지·겹치는 실행·차단 범위. 측정하지 않은 시간은 개념도라고 표시 |
| 조건별 결말이 왜 다른가? | 같은 경로를 나란히 비교하는 작은 그림들 | 갈라지는 조건·중단 위치·남은 상태·재시도나 복구 결과 |
| 어떤 상태 전이가 가능한가? | state graph, 필요하면 수명주기·연산별로 분리 | guard와 그룹 사이 전이. 반복한 node는 같은 상태임을 표시 |
| 어떤 자원 한도가 적용되나? | 수치 막대 또는 임계값 눈금 | 단위·분모, 포함 관계인 한도와 별도 몫의 구분, 실측과 예시의 구분 |
| 정확히 어떤 필드·설정이 다른가? | 표 | 동일한 비교 기준. 조회용 정보를 억지로 그림으로 만들지 않음 |

한 문서 안에서도 단일 상호작용은 sequence, 상태 변화는 state, 예외 차이는 갈래 비교가 적절할 수 있다. 잘 맞는 형식은 유지하고 관계를 가리는 형식만 바꾼다. 한 레이아웃이 실패했다고 모든 그림의 도구를 일괄 교체하거나 강제하지 않는다.

## 시각적 선택에 일관된 의미를 준다

작은 시각적 어휘를 명세에 기록하고, 실제 구현은 diagram-design에 맡긴다.

- 모든 상자에 새 색을 주지 않는다. 관련 그림에서 추적할 소수의 역할·분류에 색을 배정한다. 배경 구조는 중립색, 채움은 절제된 연한 색, 핵심 관계는 더 뚜렷한 선·강조색으로 표현한다. 합의한 팔레트를 따르며 특정 색상 코드를 보편 규칙으로 삼지 않는다.
- 대상의 정체성을 나타내는 색과 상태를 구분한다. 대상의 색이 오류색과 비슷하면 실패에 라벨·기호·패턴도 붙인다. 특정 그림에서 색의 의미를 바꾸면 범례로 밝힌다. 색 하나가 문서 전체에서 고유 식별자인 것은 아니다.
- 구조가 보이는 도형을 쓴다. mailbox 칸이 있는 actor, 내용 표시가 있는 파일, 순서 있는 셀로 된 로그, 반복 worker가 있는 pool, 소유 자원을 담는 경계가 예다. 단순 상자로 충분하면 그대로 쓴다. 근거에 없는 queue·disk·thread·replica를 아이콘으로 암시하지 않는다.
- 위치·포함·선 종류·화살촉·크기의 의미를 정한다. 임의 배치가 실행 순서·배타적인 경로·소유권·수치 비율을 암시하면 안 된다. 색 없이도 라벨과 도형으로 뜻이 남아야 한다.
- 연속된 그림의 이름·역할별 색·반복 기호·표시 글자 크기를 맞춘다. PNG 폭이 같다고 글자 가독성도 같은 것은 아니다. 제작자에게 실제 표시 크기를 전달하고 그 크기에서 확인한다.

## 설명에 필요한 차이를 남기고 추상화한다

그림의 질문에 답하는 데 필요한 대상과 구분을 남긴다. 소유권·개수·독립된 축·식별자 변경·순서 제약·성공과 실패의 경계가 이에 해당한다. 답을 바꾸지 않는 구현 세부는 생략한다. 개요에서 무엇을 묶었는지, 어느 상세 그림에서 펼치는지 설명한다.

동작 설명은 요청·행·파일·버전 하나를 구체적으로 정해 끝까지 추적한다. 만든 숫자는 예시라고 표시한다. 변경 비교에서는 배치를 맞추고, 그대로인 부분은 약하게, 달라지는 부분은 뚜렷하게 그린다. 거의 같은 전체 상태 여러 장을 독자가 눈으로 대조하게 만들지 않는다.

초안의 긴 설명문을 가려도 관계·변화·비교가 보이는지 점검한다. 필수 라벨과 guard는 남긴다. 목록만 남으면 본문이나 표로 옮기거나 형태를 다시 설계한다. 반대로 순서와 남은 상태가 결과를 좌우하는 실패 시나리오는 조회용 표 한 줄로 축약하지 않는다. 서로 다른 질문에 답하지 않는 본문·표·그림의 중복 설명은 줄인다.
