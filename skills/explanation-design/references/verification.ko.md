# 검증과 개선

검증 도구가 측정하는 범위를 넘어 성공을 주장하지 않는다.

| 층 | 확인 | 증거 |
|---|---|---|
| 구조 | frontmatter·reference·JSON·asset·링크·export 파일 | 실행 명령·exit/result |
| 근거·의미 | 주장과 출처, 인과·실행·제약·실패, 본문/표/그림 일치 | 읽은 위치·계산·실행 시나리오·수정 내역 |
| 시각 | 실제 render의 잘림·겹침·폰트·방향·축·가독성·좁은 화면 | 실제로 본 PNG/HTML·viewport·발견한 결함 |

## 품질 질문

- 첫 문단이 핵심 질문에 답하는가? 독자가 결론과 한계를 다시 설명할 수 있는가?
- 중요한 주장에 재확인 가능한 근거가 있는가? 사실·추론·제안·미확인이 섞이지 않았는가?
- 입력 → 처리 → 상태 변화 → 결과 사이에 비약이 없는가?
- 결과를 바꿀 제약·실패·반례를 빠뜨리지 않았는가?
- 선택한 표현이 이해를 늘리는가? 짧은 질문에 과잉 제작하지 않았는가?
- 그림의 edge·순서·단위·범위가 본문과 같은가? 생략이 보장을 왜곡하지 않는가?

## 전체 제작에 앞서 의미를 점검한다

그림 묶음은 대표 구조도 하나와, 필요하면 흐름·실패 그림 하나를 먼저 제작해 확인한 뒤 같은 시각적 어휘를 전체에 적용한다. 이미 알려진 사용자 선호를 따른다. 이는 검증 단계이지 새로운 승인 절차가 아니다. 마지막에는 납품할 전체 그림에서 이름·기호·크기와 대표 그림에서 발견한 결함 유형을 점검한다.

결론에 영향을 주는 그림마다 구체적 예시를 추적한다. 라벨뿐 아니라 배치가 암시하는 주장도 확인한다. 화살표는 없는 순서를, 나란한 두 경로는 배타적인 연결을, 포함은 없는 소유권을, 막대는 실제로 겹치는 한도가 별도 몫이라는 해석을 만들 수 있다. 소유권은 runtime 인자와 인스턴스 식별자까지 추적한다. 공용 helper 호출이나 식별자 등장 횟수만으로 서로 다른 프로세스가 같은 객체를 쓴다고 단정하지 않는다. “항상·유일·전부”의 범위를 확인한다. 설계 이유가 그럴듯해도 뒷받침하는 근거가 없으면 추론이다.

실제 표시 크기에서 읽는 순서·선 끝점·교차·잘린 라벨·글꼴·대비를 확인하고, 다른 렌더러로 만든 그림끼리 글자 크기도 비교한다. 기하 검사는 결함을 잡을 수 있지만 그림이 의도한 뜻을 전달한다는 증거는 아니다. 깨진 그림을 통과시키려고 검사를 약화하지 않는다. 오탐의 원인과 실제 렌더를 각각 확인한다.

## 수정이 최종 산출물까지 이어지는지 확인한다

주장이나 용어를 바꾸면 본문·표 → 그림 수정 원본이나 생성기 → SVG·PNG·export → 문서 참조 → 해당 시 게시된 파일·화면까지 따라간다. 원본을 고쳐 산출물을 다시 만든다. 다음 생성 때 되돌아갈 생성 파일만 수작업으로 고치지 않는다. 영향을 받는 모든 표현에서 폐기한 주장을 찾아보고, 바꾼 말은 문맥으로 확인한다. 모호한 낱말 하나가 서로 다른 개념을 가리켰을 수 있다.

낡은 산출물이 남을 위험이 있으면 해시나 재생성 비교를 사용한다. 이는 파일 일치 검증이며 사실 여부나 화면 표시 검증은 아니다. 업로드 성공·HTTP 200·이미지 참조 개수만으로 독자가 그림을 볼 수 있다고 단정하지 않는다. 실제 파일 형식과 이미지 해석 가능 여부를 확인하고, 접근할 수 있으면 게시 화면을 연다. 원본과 렌더의 일치, 업로드 바이트 일치, 사용자 화면 표시는 각각 구분해 보고한다. 이후 개정을 위해 수정 원본과 첨부 파일의 대응을 보존한다.

## 실행과 수정 기록

깊이 있는 설명은 독자의 목표로 돌아가 조건 하나를 조금 바꿔 확인한다. 다른 가정은 유지하고, 실패 시점을 공개 경계 전후로 옮기거나 공용 helper에 전달하는 인스턴스 ID를 바꾸거나 자원 한도는 두고 사용량을 바꾼다. 설명에서 결과를 도출한 뒤 출처와 대조한다. 필요한 경우 결과가 그대로이거나 알 수 없게 되는 사례도 포함한다. 답하려면 설명에 없는 규칙이 필요할 경우 정답지에만 그 규칙을 추가하지 말고 설명을 보완한다. 요청 크기에 맞춰 수행하며 짧은 답변마다 사용자에게 퀴즈를 내지 않는다.

바꾼 조건·예상 결과 또는 미확인·근거·수정 사항을 기록한다. 작성자의 자체 검토, 독립 agent의 과제 수행, 실제 독자의 이해도는 서로 다른 증거이므로 바꿔 보고하지 않는다. 독립 평가 prompt에는 평가자용 정답과 기준을 넣지 않는다.

현실적인 입력을 실제로 풀고 결과를 평가한다. 정답 문구를 regex로 맞추는 것은 행동 평가가 아니다. 코드·설계·데이터처럼 성격이 다른 요청에서 확인한다. 발견한 문제는 원인과 수정을 기록한 뒤 해당 사례를 재확인한다. 다른 사례에도 유효한 일반화인지 확인하고 예제 특화 규칙의 누적을 피한다.

시각 결과를 열어보지 않았다면 “시각 미검증”. browser/export 도구가 없으면 가능한 구조·의미 검증을 완료하고 실제 한계를 명시한다. syntax 통과만으로 설명 품질·시각 품질을 통과 처리하지 않는다. 독립 평가를 수행했으면 평가 입력·자율성·범위와 실제 산출물을 보존한다.
