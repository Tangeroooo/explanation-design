# 설명 순서

문서의 각 부분에 `독자 질문 → 핵심 답 → 근거 → 다음 질문`이 있어야 한다. 섹션 수는 고정하지 않는다.

추천 기본 순서: 직접 답 → 꼭 필요한 개념 → 입력 하나의 흐름 → 실패·선택이 바뀌는 조건 → 판단·행동. 독자가 원인 조사를 요청하면 관측된 증상과 그 조건에서 시작한다.

예: “왜 ack 실패 후 중복이 생기는가?”

1. 답: 전송 성공과 ack 성공이 하나의 atomic operation이 아니기 때문이다.
2. 필요한 개념: ack는 처리 완료를 broker에 알리는 별도 호출이다.
3. 흐름: send 성공 → ack 실패 → broker 상태 미확정 → 조건부 재배달.
4. 한계: broker 정책과 sink idempotency는 별도로 확인해야 한다.
5. 대처: 관측·재시도 범위 확인 후 중복 허용 또는 deduplication 결정.

모듈 목록을 이 순서의 대체물로 쓰지 않는다. 그림이 있으면 본문에서 먼저 읽을 이유를 주고, 그림 뒤에서 결론과 생략 범위를 설명한다. 캡션에 중요한 조건을 모두 숨기지 않는다.

처음 접하는 시스템은 간결한 구조 지도를 먼저 보여주고 시나리오를 따라간다. 다음 질문에 필요할 때 지도 속 특정 component·객체·경계·edge를 확대한다. 그림을 바꿔도 같은 대상의 이름과 시각적 역할을 유지하고, 어느 부분을 확대하는지 짚는다. 흐름에서는 앞서 본 구조 중 필요한 부분만 다시 보여줄 수 있다. runtime 역할, 소스 모듈, 배포 인스턴스를 구분한다.

상세 그림은 색뿐 아니라 개요의 의미를 보존해야 한다. 개요 요소와 상세 인스턴스·구성 부분의 대응, 개요 edge와 그것이 요약한 경로의 대응을 밝힌다. 새로 보이는 경로는 앞에서 생략한 것임을 알리고, 논리적 역할에서 배포 인스턴스나 소스 모듈로 관점을 바꾸면 명시한다. 같은 객체나 요청을 이어서 추적해 대응을 확인할 수 있게 한다. 상세 근거가 개요의 보장과 충돌하면 불일치를 합리화하지 말고 개요를 고친다.

목적·구조·동작·실패 조건은 내부 누락 점검 기준으로 쓴다. 필수 소제목이나 기능마다 그림 네 장을 만드는 할당량으로 쓰지 않는다. API 이름이 등장하거나 문단이 일정 길이를 넘었다고 설명이 완성된 것은 아니다. 독자가 해당 동작을 따라갈 수 있어야 한다. 피드백에서 결함 유형이 드러나면 지목된 예시뿐 아니라 요청 범위 전체의 같은 유형을 그림까지 함께 점검한다.

초안을 줄일 때 먼저 반복과 배경을 줄인다. 결론을 바꿀 오류·제약·불확실성은 남긴다. 각 문단이 새 질문에 답하지 않으면 합치거나 삭제한다.
